# AxonMind 产品与工程规划

## 1. 产品定位

AxonMind 是一个以“本地优先、端到端加密、可检索”为核心的安全知识与凭据工作台。它不追求替代所有网盘、密码管理器和项目平台，而是为小型研发团队提供一个可信入口，把最常用的文档、密钥和项目上下文安全收拢、检索并调用。

核心价值按优先级排序：

1. 数据可信：默认本地保存，敏感数据加密，云端只保存密文。
2. 找得到：统一搜索标题、标签和正文，支持本地向量检索。
3. 用得起来：添加、查看、搜索、同步形成完整闭环。
4. 可协作：个人空间与用户组严格分离，权限与组密钥边界清晰。
5. 可扩展：外部知识库、飞书 Wiki 和模型属于增强能力，不阻断本地核心流程。

## 2. 当前产品边界

### 已进入主流程

- 本地账号、恢复码与会话。
- 文本、密钥、链接、视频链接和文件入库。
- 本地加密、全文检索和可选向量检索。
- 密码库与 Git/SVN 账号、仓库管理。
- 用户组、角色、邀请、组密钥和内容复制共享。
- 飞书 OAuth、加密文件、manifest 与完整同步。
- OpenAI-compatible/Claude 等模型和外部知识源。
- 应用版本检查与更新。
- 原子数据库写入、滚动备份、完整性校验恢复和恢复前保护性备份。
- 敏感剪贴板自动清理、登录失败限流和空闲自动锁定。

### 暂不进入主流程

- 钉钉集成：当前没有真实授权、接口或持久化，不进入正式导航。
- 完整密码管理器能力：自动填充、浏览器扩展、泄漏监测不在当前版本范围。
- Git 托管平台完整替代：Issue、看板等仅适合后续在真实 API 支撑下逐步开放。

## 3. 核心用户路径

### 首次使用

注册 → 明确展示并保存一次性恢复码 → 进入工作台 → 添加第一条内容 → 在知识库中打开或搜索。

### 日常知识使用

选择个人/团队空间 → 搜索或浏览内容 → 打开可信结果 → 必要时继续知识问答。

### 多设备同步

选择 AxonMind 托管 / 个人自建 / 企业自建 → OAuth 登录 → 设置加密口令 → 主设备创建云端账号 → 新设备使用同一邮箱建立本地解锁账号并加入已有云端账号 → 自动双向同步 → 按配置自动下载密文并解密入库。

个人自建与企业自建继续使用无中转服务的直连方案：飞书 openId 的哈希只用于发现对应的加密账号文件。AxonMind 托管模式只代理 OAuth 授权和令牌刷新，不接收知识库明文；账号资料、设备列表、manifest 和内容仍以密文保存到用户的飞书云盘。稳定 Vault ID 负责跨电脑识别同一账号，本机随机 user ID 和本地密码不上传。

### 团队协作

创建用户组 → 邀请已注册成员 → 分配角色 → 从个人库复制内容到组 → 成员离开时移除并轮换组密钥。

## 4. 信息架构

- 概览：真实数据、启用状态、最近内容与快捷动作。
- 知识库：内容浏览、过滤、预览、搜索和问答。
- 密码库：敏感条目与项目凭据。
- 添加内容：统一采集入口。
- 用户组：成员、权限、共享内容和组密钥。
- 项目仓库：账号、仓库和明确受控的 Git/SVN 操作。
- 同步中心：飞书连接、上传、manifest 与同步历史。
- 设置：模型、知识源、安全恢复和更新。

## 5. 工程边界与不变量

- Renderer 不直接访问 Node、文件系统或数据库，只能通过 preload 白名单 IPC。
- 每个读取或写入操作都必须在主进程重新校验当前用户及个人/组权限，不能只依赖界面隐藏。
- 明文密码、密钥和云端口令不进入公开状态、日志或搜索结果列表。
- 个人内容不会因切换到团队上下文而自动共享；共享必须产生明确副本或显式授权。
- 每台设备写入独立的 manifest v3 分片，同步时先汇总全部远端分片、识别冲突并合并，再上传本机分片，避免并发覆盖。
- 同步由登录、启动、内容变化和定时器自动触发；离线失败采用退避重试，冲突策略与内容自动落地范围均可配置。
- 个人 manifest 必须校验 Vault ID；删除操作必须生成墓碑并参与合并，不能仅物理删除本地行。
- 同名云端账号资料和 manifest 只读取最新版本，成功上传新版本后清理旧副本。
- 演示数据和未接通的第三方能力不得出现在可操作的正式导航中。

## 6. 迭代路线

### Now：建立可日常使用的核心闭环

- 保持注册恢复码、添加、浏览、搜索、解锁与删除的端到端测试。
- 统一页面布局与语义色，清除亮色主题对硬编码选择器的依赖。
- 给同步与模型配置增加更明确的就绪检查和错误恢复指引。
- 为主进程 IPC 增加输入验证和权限回归测试。

### Next：可靠性和可维护性

- 将过大的 `src/main.js` 按账户、内容、同步、知识检索和项目模块拆分。
- 建立统一的运行时输入 schema，替换 renderer 中的 `any`。
- 完善备份导出格式、定时恢复演练和跨版本迁移验证。
- 为搜索结果提供统一详情页，而不是由不同来源各自处理。
- 增加 Windows/Linux 打包与最小窗口尺寸视觉回归。

### Later：经验证后扩展

- 真实钉钉 OAuth、消息与文件 API；完成前保持“规划中”。
- 可审计的团队活动记录和细粒度共享权限。
- 浏览器扩展或系统级快速搜索入口。
- 在真实托管平台 API 支撑下开放 Issue/看板能力。

## 7. 质量门槛

每个可发布版本至少满足：

- `npm test` 通过。
- `npm run build:ui` 通过且无 TypeScript 错误。
- `npm run test:sync` 的双设备合并、删除传播和设备注册测试通过。
- macOS 打包后执行 `npm run test:package`，并保持 ARM64 DMG 小于 120MB 的体积预算。
- 注册恢复码、添加内容、内容搜索、密码库、用户组、项目、同步配置和主题 E2E 通过。
- Electron renderer 无未处理异常和关键 console error。
- 960×700 到 1500×960 的主要页面无横向溢出或关键操作遮挡。
- 任何涉及加密、权限、删除或同步语义的变化都有对应测试或人工验证记录。

## 8. 当前已知技术债

- `src/main.js` 同时承担数据库、业务、网络与 IPC 编排，修改风险偏高。
- 多个旧页面仍包含硬编码 HSL 色值，亮色主题需要逐页迁移到语义 token。
- 前端 IPC 参数大量使用 `any`，编译期无法完整发现契约漂移。
- E2E 是独立脚本，尚未形成统一 test runner 和 CI 报告。
- 飞书 API 的真实账号连通性仍需发布前人工验证；自动化覆盖加密账号、双设备合并、删除传播和打包应用启动。
- 方案 A 不提供服务端实时推送、远程强制注销或已下载密文撤回；这些能力若成为刚需，需要评估自建同步服务的方案 B。
